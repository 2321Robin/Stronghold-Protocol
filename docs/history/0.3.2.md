  It needs no extractor dependencies or official files. `ci.yml` and its exact `test/ci.test.js` contract are unchanged.
- **[ASSUMED]:** five minutes is a CI resource budget, not a game rule. The guard checks syntax, not extractor runtime
  compatibility. It intentionally remains red until #744 merges; `fx.py` is not edited by this change.
- **Tests:** `test/local-extract-python-ci.test.js` ties the interpreter floor to setup, checks triggers/permissions,

### 35.5 Re-entrant buff removal

- **Seen:** round49's API reproduction staggers two Sargon stacks, lets the older expire, then explicitly removes
  the last stack; the call throws after clearing its ATK aggregate. The same happens after overflowing the 25-stack
  cap. An extension clearing all six members stops after the first; no current vanilla caller is known to reach it.
- **Official / contract:** local `activity_table.json` → `activity.AUTOCHESS_SEASON.act2autochess.bondInfoDict.sargonShip`
  specifies independent stack durations and equal-duration ATK for six different members.
  `effectBuffInfoDataDict.bondeffect_sargon` → `act1autochess_bond_eff_sargon` gives ASPD +12, ATK +12%, duration
  `5 + 0.22L` seconds and cap 25, disabled ATK in `band_narant`. These gameplay rules remain unchanged.
  The requested fix defines the remake's helper traversal; official tables do not specify JavaScript callback order.
- **Cause:** `removeBuff` walks the mutable list backwards by index. Sargon's synchronous `onRemove` calls `syncAtk`,
  which removes the ATK aggregate when the final stack disappears. After `[S1, A, S2]` becomes `[A, S2]` by expiry,
  removing S2 also removes A; the outer loop then reads `undefined.key` through its stale index.
- **Now:** fix the matching objects in reverse order before callbacks, then find each in the current list by identity.
  Only present objects pass through `_removeBuffAt` and count toward this call's return value; nested removals have
  their own counts and skipped objects receive no second callback. The existing path preserves intermediate stack
  counts, dirty stats, flags, status events and `onRemove` versus `onExpire`. A clearing hook can finish all six units
  and continue; its `once` handling remains intact. Normative additions: design/engine.md §5.3, SIM.md §3 and DESIGN index.
- **[ASSUMED]:** fixing this call's candidate set, retaining reverse callback order, skipping already removed objects
  and leaving new same-key instances for later calls are extension API policies, not additional official game rules.
  Explicit clearing in these tests models a plugin / kit call, not a demonstrated vanilla gameplay trigger.
- **Tests:** `test/content/sargon-remove-buff.test.js` covers the staggered two-stack / ATK case and a six-member
  extension batch at the 25-stack cap, including unique reverse callbacks, per-removal ATK sync and continuation.
  `test/sim/remove-buff.test.js` covers nested matching / unrelated removals, actual counts, flags, status events,
  callback-added same-key instances and absent-object / null no-ops. All four fail before the fix.
  Golden scenarios must remain unchanged; neither the golden tool nor its JSON files are modified.

### 35.7 AI strategy extension interface (#673, @HankDUMPLINGZhong)

- **Seen:** alternative AI policies previously required changing the built-in bot. PR #673 by
  **@HankDUMPLINGZhong**, cherry-picked as `4908a73b`, provides the strategy framework.
- **Official / decision:** maintainer review of #673 permits the implementation extension; no official gameplay
  rule or default policy changes.
- **Cause:** match decisions and tooling were coupled to the original functions.
- **Now:** per-match validated strategy definitions, inherited hooks, registry selection, startup validation,
  sliced prep/rehearsal and journal identity. The original implementation remains `legacy`.
- **[ASSUMED]:** this server implementation contract and benchmark experiment selection are engineering policy,
  not an official alternate AI rule. The original #673 description and validation follow.

Source: maintainer review of PR #673. Normative contract: DESIGN §6.6; implementation reference:
[META §1.6](../META.md#16-selectable-ai-implementations) and [the strategy guide](../BOT_STRATEGIES.md).

Match resolves a trusted server-side AI definition per match: an explicit `botStrategy` option (ID or definition)
overrides `SP_BOT_STRATEGY`. An unset or empty selection uses the original bot, `legacy`, the only built-in at #673.
`botStrategyContract.js` provides frozen definitions that inherit unspecified hooks and pure registries that
reject duplicate IDs. Implementations import the contract, separately from the registry, to avoid import cycles.
`startServer()` validates the environment selection before loading data or listening, reporting the variable,
rejected value, available IDs and how to restore the default when the ID is unknown.

Band/card/private-bounty picks and both sliced prep stages use the selected object. Match still owns cancellation,
host-delegated rehearsal, cleanup and Ready, including exceptions thrown before an iterator exists. Prep generator
steps are counted by `testSlice`, and local rehearsal jobs receive the same slice controller. Replays use the
journalled step budget instead of wall-clock timing, so inputs between slices keep their original order.
The input journal records the resolved `botStrategy` ID; replay explicitly uses it, with `legacy` for older records
that omit it, regardless of `SP_BOT_STRATEGY` on the replay host. An unavailable recorded ID fails explicitly.

Matchrun and botbench select registered IDs; benchmark records and bounty calibration use the selected bot.
Solo `--band` forces only the opening picker, preserving `gd.bandIds()` / `gd.bandBondIds()` for later effects and
skipping the original picker's RNG draw. The earlier override replaced both methods for the entire match;
these are different experiments and require fresh comparison runs.

No alternate policy, new weights, extra legacy RNG draws or priority AI seats ship with this interface. Band
selection keeps the existing draft order, including the room's existing AI-last option. General and specialist
policies are future, separate contributions. The original `bot.js` policy and legacy Golden results stay unchanged.

- **Tests:** real HTTP/WebSocket room startup with unset/empty/explicit legacy selections, inherited hooks,
seeded choices/RNG, match isolation, private drafts, sliced prep/rehearsal replay and failure cleanup. Recorded and
old journals are replayed after changing the environment, checking strategy identity, state and RNG.

### 35.8 External AI strategy (maintainer request 2026-10-19)

- **Seen:** #673's synchronous pickers and prep generators cannot exchange decisions with a host program or
  third-party service; calling network IO there would block or race phase progression.
- **Official / decision:** binding maintainer decision **2026-10-17**, requested **2026-10-19**: an external AI
  API, “observation → intents, validated like a human, timeout → built-in bot”, as a #673 strategy. This is a
  remake extension; existing official economy, placement, drafts and phase rules remain in DESIGN §6 / META.
- **Cause:** `Match.handle` authorizes human seats, while the original bot mutates through trusted hooks; the
  test journal previously recorded only the selected implementation and scheduler slices.
- **Now:** registered opt-in `external`, asynchronous band/card/prep/offer decisions, exact public and own-private
  wire views, incremental human intents, shared semantic validation and human schema/error codes. HTTP(S) POST
  accepts no redirects, bounds replies and time; stdio multiplexes one persistent child per match, kills it on
  failure and restarts on demand after backoff. Accepted actions survive fallback; legacy completes the decision
  with existing sliced prep/rehearsal. Stale replies cannot apply across turns/phases or manual takeover.
  Journals store external replies/failures and non-secret limits; replay does not contact the AI. Default
  `legacy`, #673 authorship, human seat authorization and normal golden results stay unchanged.
- **[ASSUMED]:** `sp-ai/1` envelope and gameplay-action allowlist; 1000 ms total decision/request budget, at most
  half the remaining phase time; 64 intents per decision, 64 KiB replies, 3 consecutive failed decisions before
  match-long legacy for that seat, 1000 ms restart backoff; configurable bounds and seat selection. Stdio has
  no shell, discards stderr and uses SIGKILL for cleanup; examples choose simple public-view actions. These
  are engineering choices, fully specified in [External AI API](../EXTERNAL_AI.md), with a
  [Chinese server-owner guide](../EXTERNAL_AI_ZH.md). No new gameplay assumption.
- **Tests:** `test/match/external-ai.test.js`, `test/match/external-transports.test.js`, startup/strategy tests,
  related match, test-mode and documentation suites; envelope bounds, view equality/isolation, human rejection,
  both transports/examples, all failure paths, cutoff, stale replies, personal/plugin choices, offline replay
  and full real-simulation bot matches with one external seat and a legacy peer. Golden unchanged; no UI msgids.

Validation summary: related match/startup/test-mode run `# tests 1067`, `# pass 1067`, `# fail 0`;
final external suites `# tests 35`, `# pass 35`, `# fail 0`; docs `# tests 32`, `# pass 32`, `# fail 0`.

#### 35.22.1 The registry and the version identity

`shared/versions.js` is pure and browser-safe. It defines `DEFAULT_VERSION = 'act2autochess'` and a frozen `VERSIONS`
table (the four versions of the decision above, in that order: the default first), with the helpers `versionById`,
`versionSlug` and `versionOfData`.

- An id is the official activity id (activity_table `AUTOCHESS_SEASON`). A sub-version adds `@<versionInfoDict id>`;
  the id without one is the season's final sub-version.
- Paths and file names use the slug: lowercase, with no `@` (`act1autochess-v1_1`, `act2autochess-v2_1`).
- Data, rooms and logs without a version mean the **code constant** `act2autochess`, never a server setting. A server
  that changes its default therefore never re-labels old logs or replays.
- A non-default build carries `config.version = { id, family, rules }` as the last key of `config.json`. The default
  build has no such key. `versionOfData(data)` reads that key.
- The labels (第一期上半 / 第一期下半 / 第二期上半 / 第二期下半) are msgids in the four UI packs; their translations are
  [ASSUMED]: zh-TW the same words, en "Season 1 · Part 1" … "Season 2 · Part 2", ja 「第1期・前半」 … 「第2期・後半」, ko
  「1기 · 전반」 … 「2기 · 후반」.
- There is no `data/versions/index.json`: M1 reads the registry.

#### 35.22.2 The default version is pinned

The switch must not move the default by one byte. The original cs is the exception: it hashes every served code file,
so any code change moves it, and only its formula is pinned. The guard was recorded on the untouched tree before any
other M0 change, in `test/versions-default-guard.test.js` and `test/fixtures/versions-default-guard.json`:

- **G1**: the sha256 of the 22 tracked default data files (top-level `data/*.json` and `data/i18n/*.json`, never
  `data/versions/`) and of the golden corpus `test/golden/*.json`. Hand checks with `git diff` must use the pathspec
  `':(glob)data/*.json'`. A plain `'data/*.json'` also matches below `data/` and lists every version file. G1 is the
  M0 merge check: it proves that the M0 commits moved neither, and it is **deleted when M1 starts**. After that
  `test/golden.test.js` and the rebuild check of `test/data.test.js` guard both, as before M0. Until then an intended
  golden update or default data rebuild refreshes the fixture in the same commit
  (`SP_UPDATE_GUARD=1 node --test test/versions-default-guard.test.js`, named in `test/golden/README.md` and DATA.md).
  The fixture holds `db8e226d`'s hashes. When the branch M0 merges into has changed a pinned file since then (the 0.3.2
  integration branch did: §35.19 moved `data/assets.json`, `test/golden/fields.json` and `test/golden/matches.json`), G1
  fails on the merged tree although M0 moved nothing, and regenerating it blindly would hash the merged tree and prove
  nothing. The merge therefore, with `<m0>` the M0 branch tip, (1) confirms that
  `git diff $(git merge-base <base> <m0>) <m0> -- ':(glob)data/*.json' ':(glob)data/i18n/*.json' ':(glob)test/golden/*.json'`
  is empty (the pathspec names exactly the files G1 pins; M0 edits `test/golden/README.md`, which G1 does not), (2)
  runs `node tools/golden.mjs` on the merged tree (every scenario unchanged), and only then (3) regenerates
  the fixture with `SP_UPDATE_GUARD=1` in the merge commit, whose message says the base moved and by which sections.
- **G2**: the default `config.json` has no `version`. The gameplay file lists and the vanilla content cover exactly the 16
  top-level files, nothing under `data/versions/`.
- **G3**: the cs formula, through known-answer vectors of `shared/plugins/identity.js`, and `CONTENT_HASH_VERSION` 1.
- **G4**: a fresh co-op / NORMAL `room.state` deep-equals the fixture. The code, ids, name and `content.cs` are
  normalised; `content.cs` must equal the welcome's vanilla hash. The welcome has no `versions`.

G2–G4 stay after M1.

#### 35.22.4 Behaviour keyed by charId and effectId

#### 35.22.5 The blackboard audit (the M2 work list)

`node tools/bb-audit.mjs --data <dir>…` (with `--json` and `--strict`) reports five kinds of gap for each version
directory, compared with the default data:

- the blackboard fields the version lacks that the code reads with a default, flagged when the default is not neutral;
- the buff keys the code names that the version lacks;
- the skill trigger rules of its chess, backups and tokens that the engine does not implement
  (`shared/plugins/skillSpec.js TRIGGER_RULES`);
- the keys the version carries that the default data lacks and no code under `server/` or `shared/` names, each with
  its records: the buff key and `bbStr.key` of bands, bonds, items and effects, and each garrison's `effectType`,
  `effectKey`, `battleRuneKey` and `bbStr.key`. The first three compare records by id or key, so they never see these.
  Such a mechanic is silently inert: `garrisons/meta.js` runs `H[effectType]` and `garrisons/battle.js`
  `INSTALLERS[key]` only when a handler exists, without a warning;
- the blackboard fields the version carries under a behaviour key and buff the default data also has, where the default
  lacks the field (the first class the other way round), each with the code's reads of that name. A neutral default for
  a field the version lacks is harmless only when the version lacks the mechanic, not when it carries the mechanic under
  another field: those clauses look neutral in the first class and are inert. The reads are context, not a filter: a
  name the code reads elsewhere (`silence` for enemies) does not show that the clause's handler reads it.

`kits/` is skipped for the field and buff-key classes, because kits read skill blackboards. The talents of
`enemies.json` and `tokens.json` are outside every class, so a field `server/sim/content/tokens.js` reads by name is
never compared; 炎佑's V1_1 gap below comes from a hand diff of every same-id enemy and token blackboard. Fields are
matched by name across tables, so the audit over-reports (for example `atk`) [ASSUMED]. The default data audited against itself has no
finding. No class sees a record whose text changed under the same keys and blackboard fields; those are listed by hand
below (same key, different meaning).

### 35.30 Settlement penetration order (PR #798, @Siornya)

Fixed DEF/RES penetration is subtracted and clamped at zero before percentage penetration. The former order
could over-penetrate when both were present. Source: [PRTS 伤害公式](https://prts.wiki/w/游戏数据基础#伤害公式).
Core and Irene regressions cover the arithmetic.

### 35.31 Q / X prefer the selected operator, otherwise use hover (PR #859)

### 35.32 Ordered settlement pipeline and dependent consumers (PR #802, @Siornya)

The third part of @Siornya's settlement series (#796 and #798 are §35.30; #844, #855 and #856 follow in §35.33–§35.35)
replaces the v0.3.1 damage pipeline with the kernel under `server/sim/attack/`, entered only through
`server/sim/attack.js`: `dealDamage`, `dealElementDamage`, `dealHPLose`, `heal` and `healElement` take object requests
with the actual `source` and an independent `credit` (statistics and kills; `source: null, credit: owner` is attributed
无来源 damage); the positional Battle calls and the `loseHp` / `reduceElement` aliases stay and run the same kernel.
The stages follow PRTS [伤判效果](https://prts.wiki/w/伤判效果), [伤害分类](https://prts.wiki/w/伤害分类) and
[事件](https://prts.wiki/w/事件): `hit` → the source's calculation (`damageCalculate`; not for `calculation:
'precomputed'` or `'resolved'` requests) → the target's (`damageCalculateTarget`, the arts attack addition) → the DEF /
RES formula with fixed before percentage penetration (§35.30) and the source's multipliers → `damageOutput` →
`damageBeforeApply` (source) → `damageApplying` (target) → 限伤 → the target's injury effects in priority, then
acquisition order (damage-taken multipliers such as 脆弱 / 庇护, fixed reductions — the strongest per HP type —,
barriers and count shields, held dodge / block effects; a cancellation stops the later defences while observers still
run) → `hpDamage` and transfer reservations → the HP step (special HP maps only the HP delta) → `hpChanged`,
`modifierApplied`, `damageApplied`, the legacy `damaged`, fatal / kill, `onApplied`. Requests carry the native
`attackType` (NONE / NORMAL / SPLASH / BUFF / ADDITION, default NORMAL) and `applyWay`; `isAttack` is the attack
behaviour only. Current contract: SIM §4 and design/engine.md §5.5 (the damage line and "Settlement consumers and
evidence"); short examples: `server/sim/AGENTS.md`.

**Behaviour changes.** v0.3.1, now and the source of each; "templates" are the official `buff_template_data` at
[ArknightsGameResource 9bf23966](https://github.com/yuanyan3060/ArknightsGameResource/blob/9bf239661e37766fba585806fb9fa67e79bb679e/gamedata/battle/buff_template_data.json)
(the PR's pinned revision; the templates cited here were read again for this merge).
